# AUTOMATION — 多 Agent 自动化协作架构

> code-kit 的自动化执行蓝图：**能自动的全部自动；人工只在需要澄清的地方介入，阶段推进的唯一硬前置是上一阶段先沉淀输出物**。
> 核心原则一句话：**除非需要澄清、意图不明或确有疑问，否则不打扰用户；其余一切自动化。**

配套硬规则：`RULES.md` R17（自动化协作）/ R18（澄清式人工介入与沉淀前置）。
适用场景：任务已进入 `3-task` 之后（拆解完成、`<auto>` 策略已投票）；或以常驻 agent 模式挂机运行。

```
                      │  ① 主拆解 agent（3-task · Planner）          │
                      │  拆任务 → 依赖图 → 波次 → 逐 task <auto> 投票 │
                      └──────────────┬──────────────────────────────┘
                                     │ 派发（同波次并行）

                     │ 通过           │ 失败
                     ▼                ▼
      ┌──────────────────┐   ┌──────────────────────────────┐
      │ ③ review agent   │   │ ④ 日志扫描 agent（常驻）        │

               │              └──────────────────────────────┘

      ┌────────────────────────────────────────────────────────┐
      │ ⑤ 自动提交 agent（常驻）：不断扫描产物                    │
      │    DEV task 验证/审查通过 → 原子提交；阶段文档齐 → 阶段提交    │
      └────────────────────────────────────────────────────────┘
               +
      ┌────────────────────────────────────────────────────────┐
      │ ⑥ 自动拉齐 agent（常驻）：只读检查 git；扫描任务与结论 wiki  │
      │    （git 提交 / 记忆库 / 极库云）；扫描任务产物与代码，      │
      │    拉齐所有产物保持一致（= S-align 的常驻化，R15）          │
      └────────────────────────────────────────────────────────┘
```

**分工要点**：
- **① 主拆解 agent 只拆不打**：它不写代码，产出 TASK.md（波次 + `<auto>`）后即转为调度者，向子 agent 派发并收集结果。
- **前置 3 阶段（CHANGE / REQUIREMENT / DESIGN[+2a]）相互依赖、不可拆并行**——它们是同一个推理链，由主 agent 顺序完成，不存在"切分给不同子 agent"。
- **可并行的只有 3-task 之后**：任务级无依赖即同波次，切给多个子开发 agent。

## 1. 七类 agent 职责定义

| # | agent | 生命周期 | 职责 | 对应阶段/规则 |
|---|---|---|---|---|
| ① | **主拆解 agent**（Planner/调度者） | 每个 change 一个 | 顺序完成 0→1→2(→2a) 前置阶段；跑 3-task 拆任务 + 波次 + `<auto>` 投票；按波次派发子 agent；汇总各路结果；触发 S-align → 7-integration | `0-change`~`3-task`，R13 |
| ② | **子开发 agent** | 每任务一个（fresh context） | 在 read_files/write_files 边界内完成单个 task；自检 done 判定；**完成即报告，不自行测试** | `4-dev`，R6.5 边界 |
| ③ | **测试 agent** | 每任务完成即介入 | 跑 `<verify>` 命令 + 对应 AC 抽查；输出 通过/失败 + 证据；**每个完成的任务都进测试，不等波次收尾** | `5-test` 矩阵的按需切片 |
| ④ | **日志扫描 agent**（常驻） | 全程挂机 | 扫描运行日志与心跳；子 agent 失败、超时或自锁时立即报告主 agent，由主 agent 终止失活运行、核对写集并接手或重新分派；可读产物进入测试/修复 | 本文件 §5，R17.3 |
| ④' | **修复 agent** | 按需生成 | 日志扫描 agent 判定可修改后，按错误类型定向生成：修复 bug / 重跑失败 verify / 回滚越界 diff | `4-dev` 断点恢复分支 |
| ⑤ | **自动提交 agent**（常驻） | 全程挂机 | DEV task 通过 verify + review 后按 R4.1 原子本地提交；阶段文档凑齐后按 §4 提交。未验证的半成品不提交；普通本地提交不等待人工 | R4 / R10 可恢复提交 |
| ⑥ | **自动拉齐 agent**（常驻） | 全程挂机 | 只读扫描任务、提交与文档的一致性；发现漂移交主 agent 裁决并触发 S-align。工作区有活动写集时不得自动 `git pull` 改变其他 agent 的基线 | `S-align` 常驻化，R15 |

> 常驻 agent（④⑤⑥）是"挂机三件套"：扫描→提交→拉齐互相独立循环，互不阻塞。
> 在 DSH 等 harness 里对应 background job / subagent 循环；在纯对话工具里退化为"每次进入下一阶段前先跑一轮扫描"的仪式（见 §7 降级）。

## 2. 任务流转状态机（子开发 agent 的 done 之后）

```
pending → in-flight → done(自检) → testing → passed ──┬─→ reviewed ──→ 待提交
   ↑                        │              │           │
   │                        │              └─ failed ──┤
   │                        │                          │
   └── 主 agent 检查写集后接手/重派 ◀── 日志扫描 agent 报告失败/超时/自锁 ◀┘
```

- **`done` ≠ 完成**：子 agent 自检 done 只是自报，必须经测试 agent 跑 verify 通过才算数（R5）。
- **失败恢复**：日志扫描 agent 报告失败、心跳超时或自锁，不以 `done` 为唯一准入。主 agent 先终止失活运行、核对写集与可读产物；无冲突时接手或重派，存在冲突时隔离写集后恢复。损坏产物按最后可验证检查点重建；不得无限等波次收尾。
- **每个测试通过都进 review**：review agent 逐任务消费 `passed` 队列，不攒批（避免 review 上下文爆炸）。

## 3. 人工介入：澄清触发，不是固定关卡

> **人工介入不由阶段位置决定**——没有"第 N 阶段必须停"的固定关卡。唯一判据：**这里是否需要人工澄清**。
> 核心原则：除非需要澄清、意图不明或确有疑问，否则不打扰用户；其余一切自动化。

### 3.1 推进判据（默认直通）

每个阶段收尾时跑一遍推进检查：

```
阶段工作完成？
  ├─ 否 → 继续做
  └─ 是 → 沉淀输出物（工件落盘 .specs/… + STATE.md 状态行 · R18.3）
          ├─ 未落盘 → 先补盘，禁止推进
          └─ 已落盘 → 有澄清需要？（歧义 / 偏好 / 纠正 / 把关）
                      ├─ 无 → 直接进入下一阶段（不问"要继续吗"）
                      └─ 有 → 停下一次性问清 → 解决后推进
```

**直通条件 = 上下衔接清楚 + 方案清楚**：上游工件齐全无歧义、方案无平票无争议、verify 可机判——这样的阶段之间不设任何停顿，**落盘即走**。

**沉淀前置与 R2 阶段门构成双向闭环**：离开一个阶段前必须写盘（R18.3），进入下一阶段前必须查盘（R2 Artifact Preflight）。工件是阶段之间唯一的接口——对话记忆不算数。

### 3.2 澄清触发四类

| 触发 | 判定信号 | 典型场景 |
|---|---|---|
| ① 歧义 | 多个合理解读/方案无法自动收敛：调研给出 4-5 套方案、专家团平票、需求多种读法 | 想法调研审核——专家团先收敛成 4-5 套带利弊的方案，人做选择题（自动 60% / 人工 40%） |
| ② 偏好 | 审美/风格/取舍无法机判，必须人定 | UI 风格设计与逐页排版（自动 50% / 人工 50%） |
| ③ 纠正 | 人看过产物不满意，反馈驱动重生成 | 产品原型 & HTML 界面、实际测试使用——描述不满意点 → 重新生成，循环到满意 |
| ④ 把关 | 不可逆动作执行前 | push、发布、生产写入或破坏性变更（R4.6）需人工批准；普通本地原子提交可直接做 |

**③ 不是主动停顿**：产物生成后不主动等人，正常直通；人回头说不满意才触发纠正循环。UI 实界面人工过目同理——正常路径直通集成，人想看时才介入。

### 3.3 澄清纪律与法定暂停点

- **一次性问清**：同类疑问合并成一条消息，不拉锯；解决后立即推进，不复述确认。
- **需要人工的硬停点**：`<auto>false</auto>` 任务执行前、R16.7 议题 ⑤ 人审门，以及无法自行纠正且需要授权的违规动作。停下时给出证据、当前最优结论与恢复入口，不循环等待。
- 阶段门禁（R9 专家投票）全票/多数通过 → 自动进下一阶段，不问；平票已归入 ① 歧义。
- 提交标准（§4）未凑齐 → 自动提交 agent 继续等，不打扰任何人。
- 拉齐 agent 发现漂移 → 自动登记并跑 S-align 检测；合并动作涉代码才升级人工（R15：S-align 永不改 L1 代码）。

## 4. 提交标准（自动提交 agent 的准入判据）

DEV task 通过 verify 与 review 后按 R4.1 逐 task 原子提交，便于失败恢复；下表只规定阶段文档的提交时机：

| 凑齐产物（缺一不提） | commit 主题示例 |
|---|---|
| `CHANGE.md` | `docs(spec): change <id> 立项` |
| `REQUIREMENT.md` + `CONTEXT.md` 更新 | `docs(spec): <id> 需求与术语` |
| `DESIGN.md`（含 §0 技术栈选定） | `docs(spec): <id> 技术设计` |
| `UI-DESIGN.md` | `docs(spec): <id> UI 设计` |
| `TASK.md`（含 `<auto>` 投票） | `docs(spec): <id> 任务拆解` |
| 该波次全部 task 通过测试+review，代码产物落盘 | `feat(<id>): 波次 N 完成（T01-T0k）` |
| `TEST.md` 矩阵 + 执行记录 | `test(<id>): 测试矩阵执行` |
| `REVIEW.md` | `docs(spec): <id> 双轮审查` |
| `ALIGNMENT.md` + 归档套件 | `chore(spec): <id> 对齐归档` |

规则：
- **中间态不提交**：单个 task 的半成品、review 未过的 diff、被挂起的失败任务留在工作区；通过 verify + review 的 task 当轮提交。
- 普通本地原子提交不需澄清④；push、发布与破坏性变更按安全协议审批。
- R10 安全网：提交前记录任务写集与状态，只对本任务文件做可恢复快照；共享工作区不对他人改动执行 `git stash` 或硬重置。
- 未通过 verify / review 的改动在 STATE.md 登记阻塞与恢复入口，不以等待普通提交审批代替交付。

## 5. 日志扫描 agent 的判定规则

```
对每条 agent 运行日志 / 每个任务状态，扫描并分类：
├── 错误类型
│    ├── E1 边界越界（write_files 之外出现 diff）   → R6.5 拦截 → 登记回滚建议
│    ├── E2 verify 失败                             → 主 agent 核对写集后转 ④' 修复 agent
│    ├── E3 幻觉产物（引用不存在的文件/接口）          → R6 反幻觉 → 标记重做该 task
│    ├── E4 崩溃 / 超时 / 自锁                       → 立即通知主 agent；终止失活运行并接手/重派
│    └── E5 依赖等待（上游 task 未完成）              → 正常，不算错误
└── 恢复前检查：原运行已退出；写集无活动冲突；产物可读则沿用，损坏则从可验证检查点重建。
    有下游依赖时及时通知下游并重排，不把依赖关系当成无限挂起理由。
```

## 6. 自动拉齐 agent 与 S-align 的关系

拉齐 agent 是 **S-align 的常驻前置哨兵**，不是替代：

| 层 | 拉齐 agent 干的 | S-align 干的 |
|---|---|---|
| 触发 | 定时/事件式自动跑（git 有新提交、wiki 有新结论、记忆库有新条目） | 显式调用（7-integration 前强制） |
| 扫描 | 只读检查 git 状态 + 任务/结论 wiki（git 提交信息、agent 记忆、极库云文档）+ 任务产物 + 代码 | 五层（代码/原型/活文档/决策留痕/执行留痕）全面比对 |
| 动作 | 登记"哪里可能不一致"，产出候选漂移清单；轻微文档漂移可直接修（非 L1 代码） | 按 D1-D6 判定规则出正式 ALIGNMENT.md + 合并动作清单 |
| 代码 | **永不改代码**；涉及代码的合并 → 升级人工 | 同样永不改 L1 代码，合并需用户确认 |

**wiki/记忆/极库云**：都是"任务与结论"的存放处。拉齐 agent 三处都扫，以 git 提交信息为权威时间线，记忆库与极库云作为补充证据源；冲突时以**最近 git 提交**为准并登记冲突。

## 7. 降级策略（没有常驻 agent 能力的环境）

纯对话式 AI 工具（无后台任务）按如下降级，语义不变：

| 本架构 | 降级实现 |
|---|---|
| 常驻日志扫描 agent | 主 agent 在每个子任务结束、失败或超时后立即跑 §5 检查 |
| 常驻自动提交 agent | DEV task 通过 verify + review 即做原子本地提交；阶段文档按 §4 提交 |
| 常驻拉齐 agent | 进入 7-integration 前必跑一次 S-align（这本来就是 R15.1 强制前置），有极库云/记忆库接入时多扫一处 |
| 子开发/测试/review agent | 逐 task 顺序执行 `4-dev`（fresh context）→ 跑 verify → 小节式 review——即 code-kit 原有的单会话流程 |

有 harness 子 agent 能力（如 DSH 的 subagent/background job）时按 §1 原样部署。

## 8. 「暂缓项 = 议题」统一约定

**暂缓项和议题是一个东西**，统一叫**议题**，统一走 D-discovery 的议题机制：

- 任何阶段产生的"先不做 / 下轮再说 / 拿不准"的事项（REQUIREMENT 的 `### v2（下一轮考虑）`、DESIGN 评审被否的方向、review 提的改进建议、测试发现的非阻断问题）——**一律登记为议题**。
- 议题的存放：议题即 change（R16.5）——按议题语义 slug 建 `.specs/<change-id>/`，工件 `TOPICS.md`（状态表）/ `D-<子议题slug>.md` / `ROADMAP.md`（走 D-discovery 五步流程讨论）；轻量时只在 `STATE.md` 记一行"已留档议题 <slug>"。
- 议题的处理路径只有两条：① 立项 → **同一 change 目录补写 CHANGE.md 续走主干**（why/what 引用 ROADMAP.md 已过审结论，禁止另起第二个 change）；② 留档 → STATE.md 登记，等下一轮 D-discovery 扫描事实时自动被当作输入重新评估。
- **禁止**再造第二个概念（backlog / parking lot / 待办池）：文档里不出现这些同义词，搜索"议题"能找全所有延迟决策。
