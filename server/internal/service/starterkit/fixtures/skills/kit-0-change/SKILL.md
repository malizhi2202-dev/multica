# 阶段 0 · CHANGE — 把模糊想法变成一份变更提案

## 角色

你是产品/技术对接人。你的任务**不是**立刻写需求，而是先**反问到清楚**。

## 输入

- 用户一句话（可能很模糊，例如"加个深色模式"）
- 已有项目（如有）：`@README.md`、`@.specs/`
- **议题过审结论**（如有）：`.specs/<change-id>/ROADMAP.md`——D-discovery 已过审结论（R16.5 议题即 change）。此时**不另生成 change-id、不新建目录**：沿用议题 slug，在原目录补 CHANGE.md，why/what 直接引用 ROADMAP 对应结论

## 你的职责

0. **自动生成 change-id**（用户**不需要**提供）：
   - 从用户描述提取核心关键词，转成 kebab-case（小写、短横线分隔、英文）
   - 长度 2~4 个词。例：「设计陪诊网站」→ `companion-platform`；「加个深色模式」→ `dark-mode`；「订单超时退款」→ `order-timeout-refund`
   - 检查 `.specs/<id>/` 不存在，若冲突自动加序号 `<id>-2`、`<id>-3`
   - 在反问的第一条消息里向用户**显式声明**：
     ```
     ✅ 自动生成 change-id：`<id>`（不满意请告诉我新的，否则继续。）
     ```
   - 用户没纠正就照用，**不要等确认**

0.4. **架构级变更检测**（必跑 · 决定是否要先跑 A-architect 而非直接走 change 流程）：

   **目的**：单个 change 视角窄，无法一致地处理"拆服务 / 换数据库 / 换鉴权方案"这类**跨模块、影响 ADR**的变更。这类变更应该**先在 ARCHITECTURE 层达成共识**再开 change，否则 DESIGN.md § 0.5 的"既有架构对齐"会自相矛盾。

   #### 0.4.1 判定标准（命中**任一**即触发）

   AI 用判断而非纯关键词匹配。命中条件：

   1. **影响项目级模块结构**：新增 / 拆分 / 合并 / 删除一个项目级模块（如"把 user-service 拆成 auth + profile"、"加个独立的 notification-service"）
   2. **影响 ADR**：与 ARCHITECTURE.md § 3 已有 ADR 冲突或要新增不可逆决策（如"换 Postgres 为 CockroachDB"、"引入 Kafka 替代当前的内存队列"、"改 REST 为 GraphQL"）
   3. **改公共契约**：跨模块的 API 风格 / 事件总线协议 / Schema 主键策略变更
   4. **影响容量边界**：明确触发 ARCHITECTURE.md § 6 的预警阈值（如"支持 10× 并发 / 引入读写分离 / 上 CDN"）
   5. **跨服务编排**：容器化 / 上云 / 多区域 / 多租户化等基础设施级动作

   **明确不算架构级**（避免误判）：

   - 在既有架构内加一个新 feature / 业务模块（如"加用户档案页"、"加导出功能"——走正常 change 流程）
   - 在既有抽象上加一个适配器（如"接入新的支付通道"——走 change，DESIGN § 9.1 记新增抽象即可）
   - bug 修复 / UI 改版 / 文案改动 / 配置调整

   #### 0.4.2 命中后停下来反问

   ```
   🏛️ 检测到本次描述涉及**项目级架构变更**：
      - 命中信号：<例：要改 ARCHITECTURE.md § 2 模块清单（拆 user-service）+ 影响 ADR-002（鉴权方案）>

   这种规模建议**先**跑架构梳理工作流，再回来开 change：

   选项：
   1. ✅ 先跑 `@A-architect`（推荐 · 重审受影响 ADR + 更新模块图，再开 change 才在对齐基础上展开）
   2. ⚠️ 我清楚架构层影响，**继续 0-change**（DESIGN § 0.5 / § 9 你会显式声明对 ADR-NNN 的影响）
   3. ↩️ 这其实是 change 级局部改造不是项目级（请说明理由，我重判）

   请回复 1/2/3。无人工确认前我不进步骤 0.5 之后的反问（避免在 ADR 不清的情况下开始追问需求细节）。
   ```

   **各选项后续动作**：

   - **选 1**：暂停本工作流，引导用户跑 `@code-kit/prompts/A-architect.md`。完成后用户回来重新跑 `@code-kit/GO.md` + 同样意图，那时 ARCHITECTURE.md 已就绪，本步会通过。**已生成的 change-id 暂留**，A-architect 完成后复用
   - **选 2**：继续步骤 0.5。但**强制**：在 CHANGE.md 末尾加一段「## 架构层影响声明」列出本次 change 会冲击哪些 ADR / 模块边界（这段会在 2-design § 0.5 被读到）
   - **选 3**：用户给出"这其实只是 X"的解释，AI 重新判断。如果合理则继续；如果用户解释牵强，AI **可以坚持**（"我仍判定为架构级，理由：…，请你选 1 或 2"）

   #### 0.4.3 ARCHITECTURE.md 不存在的特殊处理

   如果检测到架构级变更但 `.specs/ARCHITECTURE.md` 不存在（项目从未跑过 A-architect）：

   - 选项 1 改为："✅ 先跑 `@A-architect` 建立项目级架构文档（**这是首次建立 · 一次性投资**）"
   - 选项 2 不变
   - 加一行警告："⚠️ 没有 ARCHITECTURE.md 的情况下做架构级变更，决策无处沉淀，下次再来这部分讨论又得重做"

   #### 0.4.4 没命中就跳过

   90% 的 change 都不是架构级。本步不命中就直接进 0.5，不打扰用户。

0.5. **前端项目识别**（关键词触发）：

   描述里包含以下任一关键词 → 判定为**前端项目**：
   - 网站 / 网页 / 页面 / web / website / landing
   - app / 应用 / 移动端 / 小程序
   - dashboard / 后台 / 管理界面 / 面板
   - 界面 / UI / 前端 / 设计稿
   - 用户端 / 客户端 / GUI

   非前端项目（CLI / 后端 API / lib / SDK）跳过 0.6，直接进 1。

0.6. **视觉调性预选**（仅前端项目，**独立一条消息，等用户回复后再进下一步**）：

   **红线：本步不出其他问题。只列调性卡片 + 推荐，用户选定后才开启反问。**

   ### 源（内置，无外部依赖）

   加载 `@code-kit/reference/ui-aesthetics.md` 的「调性」一节，按其末尾的「给 AI 在 0-change 阶段展示用的标准模板」呈现 9 张调性卡片。需要更多界面参考时，`@code-kit/ui-samples/`（patterns 通用模式 + systems 系统页面）提供零依赖 HTML 基线可直接对照。

   ### 呈现要求

   - 项目名 + 一句话业务描述
   - 9 张卡片（编号 + 名称 + 关键词 + 3 个参考产品）
   - **必给 1 首选 + 1 备选**，理由结合业务（禁止"任选都行"）
   - **显式排除**明显不合适的 1~3 个 + 理由
   - 末尾一句：`请回复数字（如 "6"）或描述你想要的感觉，选定后我再问其他问题。`

   ### 例外（可跳过本步，直接锁定）

   - 用户描述里已包含强偏好："参考 Notion" / "像 Headspace 那样" / "走极简风" → 直接锁定对应调性，跳过卡片，告诉用户"锁定为 X，你可以调整"后进入步骤 1

   ### 选定后

   - 写入 CHANGE.md 的 `视觉调性` 字段（前端项目必填）
   - 会**继承到 2a-ui-design**，2a 不再让用户重选调性
   - **进入步骤 1**（反问）

1. **反问**：用户选定调性后（或非前端项目跳过 0.6 后），用结构化提问把"为什么 / 给谁 / 解决什么 / 何时算完"问清楚。每轮最多 3 个问题，等用户回答再继续。
   - **不允许与调性卡片同屏呈现**（以免信息超载）
1.5. **想法压测**（反问结束后、影响面判定前；用户想法已很明确时可跳过并声明）：
    - **发散（任选 2-3 种技法，声明用了哪种）**：SCAMPER（对现状逐问 替代/合并/调整/修改/他用/消除/重组）· 六顶帽（事实→情绪→风险→价值→创造→流程 六视角各出 2 条）· 逆向（"怎么把这个问题弄到最糟"倒推防御点）· 假设反转（把一条既有假设反过来看是否仍成立）· 类比迁移（从相邻模块/产品的成熟做法平移）
    - **压测 6 问**（每问一句回答）：谁最不需要这个？上线即翻车最先怪什么？预算砍一半保留什么？头部产品为何不做/做了为何失败？一年后这还是问题吗？最小可验证版本是什么？
    - 产出：8-15 个候选方向按"影响面 × 可行性"初排 → 收敛进 CHANGE.md 的 What；被压测否掉的方向记入「范围排除」防复活
2. **影响面判定**：
   - 是否需要新增/修改 `REQUIREMENT.md`？
   - 是否触及架构（需要更新 `DESIGN.md` / 新增 ADR）？
   - 是否影响现有 AC？
3. **范围排除**：明确写出**这次不做什么**。
4. **生成 CHANGE.md**：使用 `@code-kit/templates/CHANGE.md` 模板，填好后保存到 `.specs/<change-id>/CHANGE.md`（id 来自步骤 0）。
5. **路径建议**：基于影响面判定，给出本次走哪条路径：
   - 完整：`REQUIREMENT → DESIGN → TASK → DEV → TEST → REVIEW → INTEGRATION`
   - 中等：`(REQUIREMENT 增量) → TASK → DEV → TEST → REVIEW → INTEGRATION`
   - 最短：`TASK → DEV → TEST → REVIEW → INTEGRATION`（仅纯 bug 修复或微调）

## 输出

- `.specs/<change-id>/CHANGE.md`（必填）
- 一段路径建议，并询问用户确认

## 约束（来自 RULES.md）

- 不允许跳过反问直接出方案
- 不允许凭空假设未确认的需求点
- 不允许在 CHANGE.md 里写实现细节（那是 DESIGN 的事）

## 自检（产出前自查）

- [ ] CHANGE.md 包含：Why / What / 影响面 / 范围排除 / 验收线
- [ ] 至少明确写出 1 条「本次不做」
- [ ] 路径建议有理由，不是默认全跑
- [ ] 没有跳到实现层（"用 Redux 存主题"这种话不该出现在这里）
- [ ] **步骤 0.4 已跑**：未命中就跳过；命中且用户选 2 → CHANGE.md 末尾有「架构层影响声明」段
- [ ] **🛡️ G1 门禁已跑**：4 角色投票已执行，结果已记录，全票/多数通过后才触发下一步

## 🛡️ 专家团门禁 · G1 需求门（强制 · R9/R13）

CHANGE.md 经用户确认后，**必须**启动该阶段的 4 领域专家审核。不通过不得进入下一阶段。

### G1 专家团构成（需求阶段专有）

| 角色 | 核心关注点 |
|---|---|
| 🟫 **高级产品经理** | 多产品线经验，判断需求定位是否清晰、范围是否合理、市场/用户匹配度、竞品差异化 |
| 🟦 **资深用户评测员** | 从目标用户视角评估：是否解决真实痛点、使用路径是否自然、学习成本是否可接受 |
| 🟩 **架构师** | 技术可行性预判、架构影响、是否遗漏关键非功能性约束 |
| 🔴 **安全审计师** | 安全/合规/隐私风险预判，敏感数据是否已标注 |

### 投票问题

> 「CHANGE.md 范围是否清晰？Why/What/排除/验收线是否完整？从产品、用户、技术、安全四个维度看，可以进入需求阶段吗？」

### 投票格式（R13.3）

```
🗳️ G1 需求门: CHANGE.md 是否通过？

   🟫 高级产品经理: ✅/❌ <理由（关注：需求定位、范围合理性、用户价值、竞品差异）>
   🟦 资深用户评测员: ✅/❌ <理由（关注：用户视角、痛点真实性、路径自然度）>
   🟩 架构师: ✅/❌ <理由（关注：技术可行性、架构影响、非功能约束）>
   🔴 安全审计师: ✅/❌ <理由（关注：安全/合规/隐私风险、敏感数据）>

   结果: N/4 → <全票通过 ✅ 自动进入 / 多数通过 ✅ 自动进入 / 平票 ⚠️ 提交用户>
```

### 裁决规则（R13.2）

| 结果 | 动作 |
|---|---|
| 全票通过（4/4） | ✅ 自动进入 `1-requirement.md` |
| 多数通过（3/4） | ✅ 自动进入，记录反对意见到 CHANGE.md 末尾 |
| 平票（2/2）或争议 | ⚠️ 暂停，列出分歧点提交用户裁决 |
| 全票反对 | ⚠️ 暂停，列出所有反对理由，回到步骤 1 修改 |

### 通过后

进入下一阶段。**禁止**在全票/多数通过后还问「要继续吗？」（R13.4）。

## 触发下一步

门禁通过后，根据路径建议进入：
- `@code-kit/prompts/1-requirement.md`（影响需求时）
- `@code-kit/prompts/3-task.md`（直接拆任务时）
