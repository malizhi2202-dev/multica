# S-align — 五层对齐（防漂移 · 持续拉齐）

> 代码、原型、活文档、决策留痕、执行留痕**五层**会随开发推进各自漂移。本流程持续检测并拉齐它们，防止"代码改了文档没改、决策变了留痕没记、原型旧了没人管"。
> **只读检测 + 报告 + 拉齐方案**；经确认后才执行合并动作。产物：`.specs/ALIGNMENT.md`（跨 change 常驻，模板见 `@code-kit/templates/ALIGNMENT.md`）。

---

## 五层定义

| 层 | 内容 | 事实来源（检测时读什么） |
|---|---|---|
| **L1 代码** | 源码 / 测试 / 配置 | 工作区文件 + git log |
| **L2 原型** | PRODUCT-DESIGN.html / UI-DESIGN.md / ui-samples 基线选用记录 | `.specs/*/PRODUCT-DESIGN.html`、`UI-DESIGN.md` |
| **L3 活文档** | README / CONTEXT.md / REQUIREMENT.md 等随代码演进应更新的文档 | 根 README、`.specs/` 各 .md |
| **L4 决策留痕** | ADR / 已锁决策 / 技术栈选定 | DESIGN.md 的 ADR 段、CONTEXT.md 已锁决策段 |
| **L5 执行留痕** | STATE.md / SUMMARY.md / PROGRESS.md / git 提交记录 | 根 STATE.md、`.specs/*/SUMMARY.md`、`git log` |

## 触发时机

- `7-integration` 进入前**强制**跑一次（R15.1）
- `M-health` 巡检时顺带建议
- 任意阶段用户说"对齐检查 / 拉齐 / 检查漂移"（经 ROUTER 路由）
- 每轮 CHANGE 归档时

## 检测协议（六步）

### 1. 划定基线

确定本次对齐覆盖的提交范围：上次 ALIGNMENT.md 记录的 HEAD（首次跑取最近 20 条或项目首个提交）。执行只读命令并记录输出：

```
git log --oneline <baseline>..HEAD        # 范围内提交
git log --name-only <baseline>..HEAD      # 每次提交触碰的文件
git status --short                        # 未提交变更（一并纳入）
```

### 2. 提交归类映射

把范围内每次提交按触碰文件归入五层（可多归），产出映射表：

| commit | 主题 | L1 | L2 | L3 | L4 | L5 |
|---|---|---|---|---|---|---|
| `a1b2c3d` | feat(auth): T03 登录接口 | ✔ | | | | ✔ |

### 3. 漂移检测（规则表）

| # | 检测规则 | 检测方法 |
|---|---|---|
| D1 | 代码变了，活文档没变 | 提交归 L1 且含对外行为变化（接口/命令/配置/依赖），但同期无 L3 文件触碰，且 README/CONTEXT 相应小节与代码现状不符 |
| D2 | 决策与代码矛盾 | L4 已锁决策/ADR 与当前代码实际不符（如决策"用 SQLite"但代码已切 PostgreSQL 且无新 ADR） |
| D3 | 原型漂移 | L2 的 PRODUCT-DESIGN.html / UI-DESIGN.md tokens、页面清单与 L1 界面代码实际布局/能力不一致 |
| D4 | 执行留痕缺口 | 提交不符合 R4.1 格式、任务无对应 SUMMARY.md、STATE.md 的当前阶段与实际不符、PROGRESS.md 残留（任务已 done 却没删） |
| D5 | 需求失配 | L3 的 REQUIREMENT AC 与 L1 实现范围出现未经 CHANGE 的偏移（悄悄扩/缩范围，R7.1 的留痕版） |
| D6 | 孤儿产物 | L2/L3/L5 里存在已不被任何代码/决策引用的文档段落或工件 |

判定要求：每条漂移必须**带证据**（commit hash + 文件路径 + 两边现状各一句），证据不齐就标"疑似"，不谎报。

### 4. 拉齐方案

逐条漂移给出**合并动作**，分为：

- **可自动合并**：AI 可直接执行的文档同步（更新 README 小节、补 SUMMARY、修 STATE.md、同步 tokens）——列出"改哪个文件哪一节、改成什么"
- **需人工裁决**：决策矛盾（D2）、需求失配（D5）——给选项不动手，建议走新 CHANGE 或 ADR 修订
- **建议删除**：孤儿产物（D6）——列出建议删除清单，等确认

### 5. 呈报（对齐报告）

按 `templates/ALIGNMENT.md` 输出到 `.specs/ALIGNMENT.md`（覆盖更新，历史轮次折叠到文末附录），当面呈报要点：

> **本次对齐覆盖提交**：`a1b2c3d..e4f5a6b`（N 条，列表）
> **五层状态**：L1 ✔ / L2 ⚠ 2 项 / L3 ✖ 3 项 / L4 ✔ / L5 ⚠ 1 项
> **漂移项**：D1×2（证据…）、D3×1… 
> **合并动作**：可自动 4 项（清单）/ 需裁决 1 项 / 建议删除 0 项
> 明确问：**"是否执行自动合并项？"**

### 6. 执行与记录

- 用户确认 → 逐项执行自动合并，每项一次原子提交，格式 `align: <层> <动作摘要>（修正 <commit> 漂移）`
- 执行后在 ALIGNMENT.md"已对齐记录"表登记：漂移编号 / 对应 commit / 合并动作 commit
- 需人工裁决项 → 建议开新 CHANGE 或更新 ADR，本流程不代办
- 全部处理完 → 更新基线 HEAD，输出"五层已对齐 ✅"

## 约束（强制）

- 检测阶段**只读**；合并动作**必须经用户确认**（R15.2）
- 不修改 L1 代码——代码层漂移只能反向反映到文档/原型/决策层，或立 CHANGE 修代码（R15.3）
- 每轮报告必须含"覆盖提交列表"与"已对齐记录"两张表——**展示合并了哪些、对齐了哪些 git 本地提交**（R15.4）
- git 不可用（非 git 仓库）→ 降级为"工作区快照对比"，明示降级并缩小到 L2/L3/L4 检测
