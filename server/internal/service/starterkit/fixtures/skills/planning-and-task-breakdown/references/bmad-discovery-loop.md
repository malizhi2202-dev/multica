# bmad-discovery-loop

> 议题发现循环：只读扫描事实文档作为唯一拆解依据，把议题拆成有据可查的子议题并逐轮讨论；装了 code-kit 时自动让位给 kit。

# 议题发现循环（事实文档驱动）

把模糊的"想改进/想调研/想讨论"变成**有事实依据、经过头脑风暴、竞品验证、GD 门背书、人工审核**的结论。

## 第 -1 步 · kit 优先（必跑，决定走哪条路）

按序探测 code-kit 安装：① `<项目根>/code-kit/GO.md` 存在；② 规范安装位置 `GO.md` 存在。
**任一命中 → 本技能立即让位**：读该 kit 的 `prompts/D-discovery.md` + `RULES.md` R16 并按其执行（议题即 change、工件 TOPICS/D-*/ROADMAP、随步落盘状态标记），**不再使用本文件下文**。两处都没有 → 走下面的自含版（无 `.specs/` 自由讨论场景）。

## 硬性约束（违反即失败）

1. **零代码改动**：全程只读。不修改、不新建、不删除任何源码、配置、测试、脚本；不发起 `bmad-build`；不"顺手改一下"。结论若涉及代码，只输出**《建议改动清单》**（改哪个文件、改什么、为什么），执行与否由用户另定。
2. **事实文档是唯一拆解依据**：每个子议题、每条结论都必须能**指回具体事实**（文件路径、代码位置、配置项、数据、用户原话）。没有事实依据的内容一律不写、不列、不猜。
3. **随步落盘 + 审核状态标**（与 kit R16.3 同语义）：五步工件**边做边写**，每个子议题文件头部带 `> 审核: 待审|通过|否决（第N轮）`；⑤ 人工审核门裁决的是**状态与晋级**——未过"通过"的结论，禁止汇入 ROADMAP、禁止被下游引用；"通过"只能由用户原话背书并记入第 ⑤ 节，AI 禁止自行改写状态标。
4. **三轮上限**：整个"扫描→拆解→讨论"最多三轮；拆不出有依据的新子议题即停止，不硬凑、不开第 4 轮。
5. 审核否决 → 带用户修改意见回到第 ① 步重跑该子议题（新轮次追加，不抹历史）。

## 触发语义（宽匹配）

- **调研类**：项目调研 / 竞品调研 / 看看别人怎么做 / 市场怎么做 / 技术方案调研
- **讨论类**：议题讨论 / 圆桌讨论下这个方案 / 评估这个想法 / 这个合理吗
- **改进类**：看看有啥改进 / 产品怎么优化 / 有什么可以做得更好 / 分析产品问题 / 迭代方向讨论

判断不准时问一句"是要走发现循环（事实扫描→拆子议题→风暴→竞品→结论→GD 门→你审核）吗？"，别猜。

## 第 0 步：扫描事实文档 → 拆子议题（强制第一步）

### 0.1 只读收集事实

- **项目文档**：README、`docs/`、PRD、spec、ADR、`CONTEXT.md`、`AGENTS.md`、issue、changelog
- **代码与配置（只读）**：目录结构、关键模块、配置文件、依赖清单
- **数据与材料**：用户提供的文件、日志、指标、用户原话里的事实
- **缺失声明**：读不到或不足，明确说"缺什么"，请用户补——**不凭空拆解**

### 0.2 拆解规则

- 拆出 **2-5 个**子议题 / 讨论点，每个必须是能独立走完五步的具体问题
- **每个子议题必须标注依据**：`依据：docs/xxx.md 第 N 节` / `依据：src/a/b.ts 的 X 逻辑` / `依据：用户原话"…"`
- 拆解逻辑要写清：为什么这个点影响主议题（现状痛点、用户价值、技术可行、竞品差距、风险点）
- **反例**：没有依据的"要不要做个 XX""是不是该优化一下"——不许列为子议题

### 0.3 落盘与推进

拆完即写 `TOPICS.md`（含子议题状态表，全部"待审"），随即逐个进入五步——拆解依据已在表中自证，**不等待确认**（用户想纠偏随时可说）。

### 0.4 拆不出的分支

实在拆不出任何**有事实依据**的新子议题 → **停止循环，不重复**：
- 明确说明"已无有事实依据的新子议题，循环停止（不进入下一轮）"
- 输出当前已有产物的汇总与《建议改动清单》
- 询问用户是否**进入下一个阶段**（进入下一个 ≠ 重复循环）

## 五步讨论流程（每个子议题都必须走完，不许跳步；每步完成即写入 `D-<子议题slug>.md` 对应节）

### ① 头脑风暴发散
调用 `bmad-brainstorming`。产出 8-15 个候选方向，按"影响面 × 可行性"初排。必须带上第 0 步的事实依据作为约束。

### ② 竞品与其他产品做法分析
调用 `bmad-deep-recon`（competitive / technical 类型，可并行）。对 Top 3-5 候选逐个查：其他产品怎么做、成熟模式、踩过的坑。无联网能力时基于知识作答并标注"未联网验证"。

### ③ 总结结论与建议
自己完成（不调技能）：**结论**（推荐 1-3 个方向 + 引用 ①② 的证据）、**建议**（每个方向一句话落地路径）、**否决记录**（被否方向 + 理由）。

### ④ GD 议题门（正式减配门禁，3 人评审团）
调用 `bmad-party-mode`，三视角对齐 kit 角色：**产品经理**（用户价值）/ **架构师或研发负责人**（技术可行性）/ **领域分析**（业务合理性）。每位给出：同意 / 有保留 / 反对 + 一句话理由。全票/多数 → 提交 ⑤；平票 → 按歧义澄清交用户拍板。

### ⑤ 人工审核门（法定硬停点）
以对话形式呈现（文件已落盘，此处只请用户裁决状态）：

> **议题**：…（依据：…）
> **结论**：推荐 X、Y
> **GD 门**：PM 同意 / 架构有保留（理由） / 领域 同意
> **影响面**：…（若涉及代码，附《建议改动清单》，声明"本流程不执行代码改动"）
> **工件**：`D-<slug>.md`（当前状态：待审）

明确问：**"此子议题是否通过？"**

| 用户回应 | 动作 |
|---|---|
| 通过 / 审核完毕 / OK | 状态标改"通过"（引用户原话+时间）→ 汇入 ROADMAP.md → 更新 TOPICS.md 状态表 → 进入下一个 |
| 有修改意见 | 状态标改"否决（第N轮）"+ 意见记入 ⑤ 节 → 带回意见回到 **①** 重跑本子议题 |
| 沉默 / 不确定 / 追问细节 | 停在 ⑤，状态保持"待审"，不进下一个 |

## 三轮重复规则

**一轮 = 一次"扫描事实文档 → 拆子议题 → 所有子议题走完五步并过审"**。每轮结束重新执行第 0 步拆解判断：**拆得出**（有事实依据）→ 继续；**拆不出** → **停止，不重复**。轮次记录写进 `TOPICS.md`。

## 产物落盘（自含版目录；随步写入，状态标记晋级）

```
discovery/<议题slug>/
  ├── TOPICS.md               议题申报 + 事实底座 + 子议题状态表 + 轮次记录
  ├── D-<子议题slug>.md        单个子议题一份：①-⑤ 五节，头部审核状态标
  └── ROADMAP.md              只汇总已过审结论 + 建议改动清单 + 落地顺序
```

清窗恢复：先读 `TOPICS.md` 状态表与各文件头部状态标，**已过审子议题禁止重跑**。

## 循环纪律

- 每步结束向用户展示产物摘要再进下一步；用户喊停就停在当前步。
- 一个子议题的一轮五步流 = ①→⑤。不通过时回到 ① 带"反对理由 / 修改意见"，不是从 ② 重跑。
- 议题名用短横线 slug（如 `onboarding-optimization`）。
- 本技能只负责"把议题想清楚"：**不写代码、不写 PRD、不发起实现**；放行后由用户决定交给哪个下游技能。
