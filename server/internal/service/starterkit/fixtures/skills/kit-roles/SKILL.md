### 专家团门禁总览（R9/R13 强制）

每个阶段的**出口**都有该领域专属的专家团审核（主干门 4 人，GD 议题门为法定减配 3 人）。不通过不得进入下一阶段 / 不得晋级下游工件。

| 门 | 阶段 | 出口触发点 | Master | 专家团 |
|---|---|---|---|---|
| **G1 需求门** | 0-change | CHANGE.md 确认后 | — | 高级产品经理 + 资深用户评测员 + 架构师 + 安全审计师 |
| **需求门** | 1-requirement | REQUIREMENT.md 完成后 | — | 高级产品经理 + 资深用户评测员 + 架构师 + 安全审计师 |
| **G2 方案门** | 2-design | DESIGN.md 完成后 | 架构师 | 架构师(M) + 研发负责人 + 领域专家 + 安全审计师 |
| **G2a UI设计门** | 2a-ui-design | UI-DESIGN.md 完成后 | — | 资深UI设计师 + 资深用户体验官 + 前端架构师 + 无障碍专家 |
| **Task 门** | 3-task | TASK.md 完成后（含逐 task 自动化投票） | — | 工程效能专家 + 架构师 + 研发负责人 + 资深测试工程师 |
| **G3 代码门** | 4-dev | 全部 task 完成后 | 研发负责人 | 研发负责人(M) + 架构师 + 资深测试工程师 + 安全审计师 |
| **测试门** | 5-test | TEST.md 完成后 | — | 资深测试工程师 + 研发负责人 + 高级产品经理 + 资深用户体验官 |
| **G4 审查门** | 6-review | REVIEW.md 完成后 | 资深测试工程师 | 资深测试工程师(M) + 架构师 + 领域专家 + 安全审计师 |
| **GD 议题门**（减配 3 人 · R16.7） | D-discovery | 每个子议题 ④ 步（结论落盘后） | — | 高级产品经理 +（前端架构师/研发负责人）+ 领域专家（无对应领域→资深用户评测员）；投票格式 R13.3；平票按歧义澄清提交用户 |

> **GD 门之后接 ⑤ 人审门**（法定硬停点，R18.2②）：GD 裁决只决定"可否提交人审"，"通过"只能由用户原话背书；未过审子议题禁止汇入 ROADMAP / 禁止立项续走主干。

> **逐 task 自动化投票**：3-task 门禁中，每个 task 由研发负责人 + 资深测试工程师 + 安全审计师投票决定「🤖 自动化」还是「👤 人工介入」。结果写入 `<auto>` 字段，4-dev 步骤 0 强制执行。

# ROUTER — 语义路由（说人话，找对入口）

> 你是 code-kit 的调度中枢。用户没有报阶段号、只说了一句自然语言时，用本文件把话路由到正确的阶段 prompt 或横向命令。
> **路由三步协议：语义分类 → 状态检测 → 交接执行。** 你自己不干活——目标 prompt 才干活。

## 第二步 · 状态检测（话语模糊或问"下一步"时）

只读检查 `.specs/` 与仓库根，判断所处阶段，**推荐最近未完成阶段，绝不推荐重来**：

| 检测信号 | 所处阶段 | 推荐下一步 |
|---|---|---|
| change 目录有 `TOPICS.md`/`D-*.md` 但无 CHANGE.md | **议题期**（D-discovery 进行中/待立项，优先于下一行判定） | 有"待审"子议题 → 续走 ⑤ 人审门；全过审且要立项 → 同目录补 CHANGE.md 续 1-requirement；暂不立项 → STATE.md 留档等下轮（R16.5） |
| 无 `.specs/` 或无 CHANGE.md | 想法期 | 小改动直接 0-change 起步；调研类先 D-discovery；新产品先 P-product |
| 有 CHANGE.md 无 REQUIREMENT.md | 需求期 | `1-requirement` |
| 有 REQUIREMENT.md 无 DESIGN.md | 设计期 | `2-design`；前端项目随后 `2a-ui-design` |
| 有 DESIGN.md 无 TASK.md | 拆解期 | `3-task` |
| 有 TASK.md 有未完成任务 | 实现期 | `4-dev`（逐任务） |
| 任务全 done 未 REVIEW | 质量期 | `5-test` → `6-review` |
| REVIEW 通过未归档 | 收尾期 | `7-integration`（强制先跑一次 S-align） |

注意：TASK.md 标 done 不等于真完成——以 STATE.md、SUMMARY.md 与 git log 证据为准（R6.3），不确定就跑 `S-align` 对齐。

## 第三步 · 交接执行

1. **单目标命中**：输出一句"▶️ 路由到 `<n>-<name>`"，然后用 `@code-kit/prompts/<n>-<name>.md` 引用该文件，把**用户原话 + 检测到的阶段状态**带过去，按该 prompt 执行。
2. **多步请求**（如"从头到尾做个 X"）：先给路线图（状态检测 + 阶段顺序），逐阶段推进，每阶段产物确认后再进下一个。
3. **歧义**（2-3 个候选）：一句话列出候选让用户选，不长篇提问。
4. **规模速判**：typo 级直接做不走流程；单会话级从 0-change 起步即可压缩（MVP 路径见 METHODOLOGY.md）；多会话级全流程。

## 深挖意图（可选加强）

用户对已有产物说"再想想 / 挑战一下这个结论 / 红队审视"时，不要重跑阶段——用批判技法就地深挖：苏格拉底式追问（逐条假设反问）、第一性原理（拆到不可再拆的事实）、预演失败（假设已上线失败倒推）、红队（专攻最弱一环）。产出一页"质疑清单 + 修正结论"追加到原产物，不另开文件。
